# Day 2 — Collection and Retrieval API Design

Date: 2026-09-13T14:11:34+05:30

## 1. Purpose of this document
This report captures the design decisions and reasoning behind the Day 2 document API work for collection retrieval and resource lookup. It focuses on the architecture and behavior expected for `GET /documents` and `GET /documents/{id}`, and explains why these endpoints should remain service-driven instead of bypassing business logic.

## 2. Collection endpoint: `GET /documents`

### Question: Why is GET /documents a collection endpoint?
`GET /documents` is a collection endpoint because it does not target one specific resource instance. Instead, it asks the system for the set of all document records currently available.

At the HTTP contract level, the operation is conceptually:
- input: no document ID
- output: a list of documents
- semantics: read all resources in the collection

This differs from `GET /documents/{id}`, which is a single-resource retrieval endpoint that fetches one exact document by identifier.

### Implementation expectation
The route should:
1. Receive the request at the API layer
2. Call `DocumentService.list_documents()`
3. Let the service delegate to `DocumentRepository.list_documents()`
4. Return the list as `list[DocumentResponse]`

This preserves the architectural flow:
HTTP -> API -> Service -> Repository -> In-Memory Store

## 3. Empty collection behavior

### Question: What should an empty document collection return?
An empty collection should return an empty JSON array: `[]`.

This is the standard REST-style response for a valid collection endpoint with no matching records. It indicates success without error and keeps the client contract predictable.

Example:

```json
[]
```

A 404 is not appropriate here because the collection itself exists; it is simply empty.

## 4. Single-resource lookup: `GET /documents/{id}`

### Question: Why does GET /documents/{id} need 404 behavior?
The client is asking for one specific resource by ID. If that ID does not exist, the request cannot be fulfilled and the system should communicate that explicitly.

The repository is responsible for checking the in-memory store, and if the lookup fails it should surface a domain-level exception such as `DocumentNotFoundError`. That exception is then mapped by the FastAPI global exception handler to a 404 response.

This is the expected flow:
DocumentRepository -> DocumentNotFoundError -> API error handling -> HTTP 404

Example error payload:

```json
{"detail": "Document with ID 'nonexistent-id' not found."}
```

This is important because a missing resource is not a validation problem or a generic server problem; it is a not-found resource condition.

## 5. Delete endpoint contract and service delegation

### Question: Why should DELETE /documents/{id} call DocumentService?
The route should not contain the deletion business logic because the route is only responsible for HTTP concerns. The business rule belongs in the service layer.

Deletion requires coordination such as:
- checking whether the document exists
- raising a domain exception if it does not
- delegating the actual removal to the repository

This keeps the route thin and preserves clean layering.

Required flow:
HTTP -> API -> Service -> Repository -> Storage

The route should simply call `service.delete_document(document_id)`. The service should validate existence and call the repository to delete.

## 6. Why an explicit response schema matters

### Question: Why should the response be represented by an explicit schema?
The response schema defines the contract between the API and the client. It makes the HTTP boundary explicit and stable.

In this codebase:
- `DocumentCreate` defines the request body shape for client -> API
- `DocumentResponse` defines the response shape for API -> client

Benefits:
- validation before business logic runs
- consistent JSON output
- clear documentation for API consumers
- easier testing of integration behavior
- strong separation between transport data and internal business objects

The schema is not the application domain model; it is the API contract.

## 7. Client-supplied vs server-generated fields

### Question: Which fields are client-supplied versus server-generated?
For a creation request,
- client-supplied:
  - `name`
  - `document_type`
  - `version`
- server-generated:
  - `id`
  - `status` (defaulted to `created`)

The `id` is assigned by the service layer, typically using a pattern like `doc-001`, `doc-002`, etc.

The status is generated by the application and defaults to `created` when the document is first stored.

This distinction is important because the API must not trust the client to provide identity or lifecycle state.

## 8. API model vs business object responsibilities

### Question: Which changes belong to the API model and which belong to the business object?
The correct split is:

API model (`src/models/pydantic_model.py`):
- request validation and response contract
- HTTP boundary concerns only
- fields for client communication
- examples: `DocumentCreate`, `DocumentResponse`

Business object (`src/data_classes/document_class.py`):
- domain representation of a document
- rules and state managed by the application
- used by the service and repository
- examples: `Document` with `id`, `name`, `document_type`, `version`, `status`

API model changes belong when the client contract changes. Business object changes belong when the application domain needs new state or logic.

Examples:
- If the API adds a new field to the HTTP request or response, update the Pydantic schema.
- If document lifecycle or validation rules change, update the `Document` business object or service logic.

## 9. Architecture self-check

- [x] Can you replace the repository implementation without rewriting the API contract?
  - Yes. The API depends on the service interface and behavior, not on a specific storage type. As long as a replacement repository implements the same document operations, the route layer remains unchanged.

- [x] Can you call the service from something other than HTTP?
  - Yes. `DocumentService` is plain Python business logic. It can be called from a script, CLI, background worker, or test without any FastAPI dependency.

- [x] Can you test the service without starting FastAPI?
  - Yes. A service test can instantiate a `DocumentRepository` and `DocumentService`, then verify validation and business rules directly in Python.

- [x] Can you test API behavior without putting business rules in routes?
  - Yes. The route layer remains thin: it validates input and returns HTTP responses. The business rules live in the service, while the API tests verify status codes, schema validation, and exception translation.

- [x] Can you explain why in-memory storage is acceptable at this stage?
  - Yes. In-memory storage is appropriate for a prototype or early architecture iteration because it is simple, fast, and focused on validating the design. It allows the team to confirm layering, validation, and API behavior before introducing a durable database and persistence concerns.

- `POST /documents` with valid payload creates a document and returns the created resource
- Invalid `POST /documents` payload returns validation error (422)

- `GET /documents/{id}` returns an existing document

- `DELETE /documents/{id}` removes an existing document and returns HTTP 204
- `DELETE /documents/{id}` for a missing document returns HTTP 404 with the expected message

These tests confirm the API contract and the service/repository layering without embedding business rules in the route definitions.

## 11. Architectural lessons
The project intentionally enforces a layered flow:

- HTTP layer handles network concerns
- API/Pydantic layer handles schema validation
- Service layer handles business rules and orchestration
- Repository layer handles storage access
- In-memory store is an implementation detail

This separation ensures the API cannot bypass core behavior simply because a request is "easy" to fulfill. Even list operations, fetches, and deletions should still pass through the service layer so validation, error translation, and business rules remain consistent.

## 12. Summary
The decisive principle for Day 2 is that collection endpoints and single-resource endpoints are still business operations, not raw storage access. The system should preserve the service layer in every CRUD path and keep the HTTP schema separate from the business object model. This makes the design clean, testable, and extensible.
